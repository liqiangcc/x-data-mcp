# 交易所来源刷新策略（窗口复用、周期全量与陈旧闸门）

Refs #446（M3 交易所来源共用入口的后续）。XDM-149。设计文档，不含代码改动；第 2 行拆分已按
owner 2026-11-01 裁决写进 [SLO](../SLO.md) 与 [DECISIONS](../decisions.md) D-66（门槛不放宽）。
**owner 已对第 7 节 Q1–Q7 全部按建议裁决（见 §7 末尾）；方案与参数已定，但实现尚未开始，
现状见第 2 节。**

## 0. 结论摘要

**owner 2026-11-01 已裁决：A + B + D（测量口径拆分），C 不采用（Q1–Q7 全部按建议，见 §7
末尾）。实现未开始。**

- **A 窗口级复用**：按 `request_fingerprint` 复用已冻结快照。窗口类来源（停复牌、公告索引）只重抓
  “开窗 + 上一个自然季度”，其余关闭窗口直接读来源库；全表类来源（上市/退市/简称）按整表快照复用，
  不做单页复用。
- **B 获取与日更解耦**：新增原子任务 `refresh_exchange_sources`（`tail` 每日 / `full` 每周），
  `run_market_update` 的四个来源派生 item **只读来源库，不再发任何交易所请求**。
- **D 测量口径**：D-63 第 2 行拆成 G1（日更写循环，不含来源获取）与 G2（来源刷新）。这不是为了
  让门禁变绿：即使来源获取归零，本代实测的实体项 551.8 s + 日历 44 s + 启动 9.8 s = **606 s 已经
  超过 600 s**，所以 G1 仍会红，原因转向实体写入路径；本设计把这个事实写清楚，不把获取时间藏进
  另一个数字。
- **C 条件请求**：生产库 1,834 条索引的 `http_etag`/`http_last_modified` **全部为 NULL**；2026-11-01
  对 5 个端点实测（7 次成功请求）**没有任何 `ETag`/`Last-Modified`/`Cache-Control`**，
  `If-Modified-Since` 被忽略（仍 200 + 全量字节）。更关键的是：即使支持 304，1,835 次请求仍要按
  1 请求/秒排队，**墙钟不降**；C 只能省字节和解析，救不了 D-63。

预期效果（按 2026-11-01 生产实测口径）：

| 指标 | 现在（每日一次全量） | A+B 之后 |
|---|---|---|
| 每日交易所请求 | 1,835 | **28**（典型） |
| 每日字节 | 23.1 MB | ~3.1 MB |
| 每日来源获取墙钟 | ~2,400 s | ~40 s（tail，在主日更之外） |
| 每周全量刷新 | 7 × 1,835 = 12,845 次 | **1,941 次**（一次 full） |
| 每周请求合计 | 12,845 | 28×7 + 1,941 = **2,137**（−83%） |
| 关闭窗口修订陈旧上界 | 1 天 | 7 天（全量周期）+ 当日 tail 覆盖最近季度 |
| 来源库增长 | 只增变更页（当前 23.1 MB） | 同左；全表位移时会多存整表（见 §5.4） |

## 2. 现状事实（2026-11-01 生产只读实测）

### 2.1 链路与代码位置

```text
item（derived:security_master / security_names / risk_warnings / suspensions）
  → exchange_source::Entry::acquire_window/windows   src/exchange_source/fetch.rs:335/348
      → fetch（bounded，1 req/s）→ 2xx → freeze_bytes  src/exchange_source/freeze.rs:97
      → parse/validate（总数、0 行、分页一致）→ record_snapshots  freeze.rs:141
      → bind（snapshot ids + parser_version + basis_status）
  → 领域写入器（整表 DELETE + INSERT）
```

- 运行内缓存 `RunCache` 只覆盖**同一次运行**的重复请求（`fetch.rs:414` `acquire_pages`；命中
  `from_cache` 不下载也不冻结）。跨日没有读取短路：`acquire_pages` 在发请求前不查索引。
- 同指纹同 sha 的重复抓取由 `SourceStore::register` 去重：不追加清单行、不新增索引行
  （`INSERT OR IGNORE`，`src/sqlite_market/exchange_source.rs:118`）。因此索引里的
  `fetched_at`/`as_of` 是**该字节第一次被看到**的时间，重复抓取不会推进它。
- 索引 `UNIQUE(source_id, request_fingerprint, snapshot_id)`：同一窗口出现**新 sha** 才会多一行。
  这正好是修订检测的天然键。

- 10-31 与 11-01 两轮之间，**关闭窗口 1,294 页 0 变更**；唯一“换了指纹”的是当季开窗

## 3. 判据

正确性 > 简单 > 性能/存储。每个方案按九项比较：

1. **PIT 语义**：有效时间、知晓时间、`as_of` 是否诚实（复用不能把旧字节盖上新日期）。
2. **修订检测**：关闭窗口被交易所改动时，多久发现、留下什么证据。
3. **AC-M3-9**：断网重放能否从来源库逐位重建，且与 live 选择一致。
4. **来源库增长**。
5. **每个数据集的陈旧上界**。
6. **对 D-63 / SLO 第 2 行的影响**。
7. **实现量**。
8. **失败模式**。
9. 组合后的复杂度。

## 4. 方案比较

### 4.1 A：窗口级复用 + 周期全量 + 修订 diff

- **PIT**：复用返回的是原快照，`fetched_at`/`as_of` 保持**首次观测日**；数据集证据里的 `as_of`
  必须由被选快照算出（整表集取 `min`、窗口集取 `max`，见 §5.3），不能再写“今天”。知晓时间
  不因复用而变。这是最诚实的一种：旧字节永远带旧日期。
- **修订检测**：关闭窗口的 sha 只在 full 里比对；发现新 sha → 新快照行（新 `as_of`）+ `revision`
  记录（窗口、旧/新 sha、旧/新 `acquired_at`）→ 数据集整体重算（三个写入器都是 DELETE+INSERT，
  修订会正确删掉旧行）。tail 只覆盖最近一个关闭季度，所以“最近季度的改动 ≤1 天发现，更老的
  ≤全量周期”。
- **AC-M3-9**：来源库保留全部字节；重放选择“同指纹取最新 `acquired_at`/sha”。停复牌重放已经是
  这个规则（`a3.rs:480` 的 `reparse_pages`），**风险警示重放不是**（`replay.rs:780`：把所有
  `sse_bulletin` 页都喂进去，只按 `source_record_id` 去重；窗口被修订时，新页删掉的事件仍会从旧页
  复活）——A 落地的前置修复。全表类要把
  “最后一次完整页集”固定进证据（见 §5.5）。
- **增长**：复用不新增；修订只多一页（11–21 KB）。全表位移时整表重存（简称 2.0 MB/次，
  上市最多 3.1 MB/次），见 §5.4。
- **陈旧上界**：停牌开窗 ≤1 天、上一季 ≤1 天、更老 ≤7 天；ST 同；简称/上市 ≤7 天（探针每天能
  “发现”，全量在刷新任务里当天补）；退市/SSE 上市 ≤1 天。
- **D-63**：请求数 1,835 → 28/日；但若复用仍在日更任务内联执行，还要加上 tail 的 40 s 与本地
  解析，写循环约 650–690 s。必须配合 B/D。
- **实现量**：中。策略表 + 读穿 + 选择固定 + 证据 + 重放修复，约 600–900 行 + 夹具。
- **失败模式**：全量任务没跑 → 关闭窗口静默变旧（用 max age 闸门兜底）；交易所改参数/分页导致
  全部指纹变新 → 全量重抓（正确但贵）；全表页集中途失败 → 不完整快照（必须靠 §5.5 拒收）。

### 4.2 B：把交易所获取从日更解耦，单独节奏

- **PIT**：与 A 相同；额外好处是“日更写循环”里不再有时钟驱动的获取，`as_of` 更容易做成输入的
  纯函数。若只做 B 不做 A，获取仍是全量，只是从每日改每周：**停牌新事件最多迟 7 天**。
- **修订检测**：只在刷新任务里，检测能力同 A；日更完全不看来源。
- **AC-M3-9**：同 A。额外要求：刷新任务的“最后一次完整全量”要可查（任务记录/状态行），否则
  重放只能猜“哪一组是全量”。
- **增长**：同 A。
- **陈旧上界**：全体 7 天，除非再叠加 A 的 tail。对停牌/退市这种“今天发生、今天要用”的事实
  太松。
- **D-63**：日更 0 请求；但来源获取并没有消失，只是换了任务。必须同时改测量口径（D），否则
  “写循环”数字好看、系统总成本没变。
- **实现量**：中偏小（新任务 + 调度 + 状态），约 500–700 行；但单独做 B 会牺牲停牌时效。
- **失败模式**：一次全量失败 = 全市场来源陈旧两周；没有 per-window 粒度，难以局部重试。

### 4.3 C：条件请求（ETag / If-Modified-Since）

- **PIT**：304 表示“表示未变”，不产生新字节；**不能**推进 `as_of`，只能推进“验证时间”。
  需要新增验证日志（否则“昨天验证过”无证据）。
- **修订检测**：验证器变化只是“可能有变”，仍要 GET 才知道哪个窗口变了；304 没有 body，
  无法 diff。
- **AC-M3-9**：重放仍只能用最后一次 200 的字节；304 验证事件不进来源库，断网重放无法复现
  “那天验证过”。
- **增长**：字节 0 增长，但验证日志按请求增长（每日 1,835 行）。
- **陈旧上界**：如果验证器可靠，可做到 1 天；但**没有证据**。
- **D-63**：**墙钟不降**。1,835 次请求仍按 1 请求/秒排队 ≈ 1,835 s；304 只省下载/解析。
  只有“集合级验证器”（一次请求证明整表未变）才能降请求数，这些端点没有。
- **实现量**：若支持则小（~200 行）；现实是 0 基础。
- **失败模式**：粗粒度 `Last-Modified` 误 304 → 漏修订且无字节证据（最危险）；服务器忽略
  验证器 → 白加头；CDN 缓存导致验证器与源站不一致。
- **结论**：不作为本轮方案。保留为后续优化：若某端点将来出现强 `ETag`，可在 full 任务里加
  `If-None-Match` 省字节，但仍不省请求数。

### 4.4 D：只改 SLO 措辞（把派生获取排除出 write-loop）

- **PIT / 修订 / 重放 / 增长 / 陈旧**：全部不变（每天仍全量重抓，数据是新的，成本也是真的）。
- **D-63**：按定义变绿，但日更仍要 ~50 min，600 s 想表达的“日更要快”没有实现；而且掩盖了
  每天 1,835 次请求的合规成本。
- **实现量**：文档。
- **失败模式**：永久性技术债；后续回归无法从门禁看出。
- **结论**：单独做不可接受；但**测量口径必须拆**，否则 A+B 的收益会被“日更任务里还剩 606 s
  固定成本”淹没，见 §6。

### 4.5 组合

## 5. 推荐方案

### 5.1 数据源分类与策略表

策略是**适配器层的声明式注册**（`source_id → 规则`），不是散落的常量；一条规则进证据，便于审计：

| source_id | 类别 | 日更 tail | 全量周期 P | 硬上限 H | 说明 |
|---|---|---|---|---|---|
| `sse_suspension` | 窗口 | 开窗 + 上一自然季度（8–14 页） | 7 天 | 14 天 | 关闭窗口复用 |
| `sse_bulletin` | 窗口 | 开窗 + 上一自然季度（2 页） | 7 天 | 14 天 | 同上 |
| `szse_delisting` | 整表 | 全表（12 页） | 7 天 | 14 天 | 便宜，退市影响股票池 |
| `sse_listing` / `sse_delisting` | 整表 | 全表（各 2 页） | 7 天 | 14 天 | 便宜 |
| `szse_listing` | 整表 | 探针 1 页；recordcount 变 → 刷新任务里全量 | 7 天 | 14 天 | 146 页 / 3.1 MB |
| `szse_short_name` | 整表 | p1 探针；仅当新行含 `ST`/`*ST`/`退` 时当天补全量，否则等 full | 7 天 | 14 天 | 375 页 / 2.0 MB；普通简称变更 ≤7 天 |

- **L = 1 个自然季度**（上一季 + 开窗），不是“L 天”。理由：窗口本来就按季度切；最近一个关闭
  季度最可能收到迟报的停牌/公告（实测 2026Q2 12 页、Q3 6 页），代价只有 8–14 次请求；更老的
  季度交给每周全量，陈旧上界 7 天。把 L 设成 2 个季度只多 6–12 页，收益不明；设成 0 则最近
  关闭季度的修订要等 7 天。
- **P = 7 天**：关闭窗口修订的陈旧上界；每周 1,941 次请求（1 req/s 下 32 min 理论下界，按实测
  1.42 s/请求 ≈ 46 min）。选周末低峰跑 full，不与日更抢锁/带宽。
- **H = 2P = 14 天**：连续两周没有成功全量 → 日更的四个来源 item **fail-closed**
  （`source_refresh_overdue`），旧版本继续可读；不让“忘了跑全量”变成静默陈旧。
- **全表探针**：`szse_listing` 用 p1 的 `recordcount`（2,905），变了当天补全量（约 1 次/周，
  146 页）。`szse_short_name` 用 p1 的 `recordcount` + p1 sha，但**只有新行含 `ST`/`*ST`/`退` 时**
  才当天补全量：简称表每天都有 0.5–1 行普通变更，若“任何变更都补全量”就退化成每天 375 页，
  与目标相反。普通简称历史（`derived:security_names`）的陈旧上界就是 P=7 天；ST 区间（会影响
  涨跌停带）仍是当天。探针只决定“今天要不要全量”，不构造数据集。
- **开窗每天都是新指纹**：`windows(today)` 的 end = 昨天（`a3.rs:197`），公告按 `quarter_segments`
  到 today；所以开窗必然要抓，不需要额外规则——**指纹稳定性本身就是复用边界**。

### 5.2 复用与选择规则

```text
for each plan (source_id, window/table):
    candidates = index rows with same request_fingerprint
    if candidates is empty: fetch (new fingerprint)
    else if policy says tail/full: fetch, then compare sha with latest candidate
    else: reuse latest by (fetched_at, snapshot_id)  # 读 blob 前校验 sha
```

- 复用前必须 `read_verified(sha)`：blob 缺失/损坏 → `source_store_corrupt`，不静默降级。
- 复用的快照 id 集合写进 item 证据（`snapshot_ids` 已有；新增 `selected_by`、`reused`、
  `fetched`、`as_of`、`verified_through`），供 `--verify-only` 与审计比对。
- 同一次运行仍用 `RunCache`；跨日复用是新的一层，键仍是规范化指纹。

### 5.3 时间语义：三个字段不要混

| 字段 | 含义 | 谁推进 |
|---|---|---|
| 快照 `as_of` / `fetched_at` | 这版**字节**第一次被观测到的日期 | 首次抓取；复用/重复抓取**不推进** |
| 事实 `known_at` | 这条事实第一次进入系统的日期 | 首次包含该事实的快照入库日 |
| `verified_through` | 我们最后一次**确认**这组指纹没变的日期 | 成功的 refresh run（tail/full） |

- 数据集证据的 `as_of` 必须由**被选快照**算出，并与 replay 同规则：整表集（A-1/A-2、简称）取
  `min(page as_of)`（“整组最早的一页有多旧”），窗口集（停牌、公告）取 `max(window as_of)`
  （“包含到哪个日期”）；**不要用运行当天**。当前 live 的 A-1/A-2 写运行日、replay 取页面的
  `as_of`；复用之后两者会分叉，`--verify-only` 会把“时钟”误报成 drift。这是 A 的第一个必改点。
- `verified_through` 只在**成功的 refresh run** 里推进，并记进 refresh-run 记录（§5.6）。fresh-init
  后没有记录时，退化为 `min(selected as_of)`（保守），不假装验证过。
- `known_at`：深市简称/ST 行目前是 `NULL`（D-61：表只有变更日期，没有发布时间）。日更时滞后
  ≤1 天还可接受；改成每周全量后，**必须**把 `known_at` 填成“首次包含该行的快照入库日”，否则
  PIT 读取会一直排除这些行（有 `known_at` 过滤时 NULL 行被排除）。coverage 口径写成两句：
  **有效时间历史从来源起点起可用；知识时间 PIT（`known_at` 过滤）从首次采集日 2026-10-31 起**——
  不要写成“简称历史从 2026-10-31 起可用”。这是诚实的，也是回填数据的固有限制。见 Q4。

### 5.4 修订、全表位移与存储

- **窗口修订**：full 发现同指纹新 sha → 新快照 + `revision` 证据（窗口、旧/新 sha、旧/新
  `acquired_at`、page_count）→ 下一次 `run_market_update` 用新字节重算。三个写入器都是
  `DELETE FROM …` + 全量插入（`suspensions.rs:145`、`risk_warnings.rs:65`、`security_names.rs:67`），
  所以“删掉一条旧事实”会被正确处理。
- **全表位移**：简称表按日期倒序，新增一行 → 所有页 sha 变 → 整表 2.0 MB 新字节；上市表按代码
  升序，001xxx 插入会位移中后部，301xxx 只在尾部。**内容寻址去重对位移无效**，这是每周全量的
  真实存储成本：简称约 2.0 MB/周（104 MB/年），上市 0–3.1 MB/周。可接受，但要在 §5.7 写明。
- **不完整页集**：多页整表一次抓取共用同一 `acquired_at`；中途失败会留下“同组缺页”，而
  `rebuild_security_names` 的注释已承认重放分不出部分组。刷新任务必须在绑定时校验
  `page_count == metadata.pagecount`、`sum(row_count) == recordcount`、页码连续；不满足 →
  `snapshot_incomplete`，**不发布**，保留上一完整组。另加“末页后再读 p1”的一致性守卫（+1 请求）：
  p1 sha/recordcount 变了 → 说明抓取期间表被改，`window_changed_mid_fetch`，重试一次后放弃。
- **0 行窗口**：仍按 `not_observed`/`unverified_zero`，绝不当“无事件”。

### 5.6 刷新任务与状态

新增原子能力（应用层，不是领域）：

```text
refresh_exchange_sources --mode tail|full [--source <id>...] [--dry-run]
  tail: 开窗/上季窗口 + 便宜整表 + 两个探针；探针变化（简称仅 ST/退标记）→ 当天补该整表（≤500 页）
  full: 全部 1,941 个指纹；逐指纹比对最新 sha，输出 changed/revision 列表
```

- 只写来源库 + 索引 + 一个 refresh-run 记录；**不写业务表**（分离点 4）。
- refresh-run 记录字段：`run_id`、`mode`、`scope`、`started_at`/`finished_at`、`requests`、
  `reused`、`changed`、`failed_windows`、`verified_through`、`task_id`。建议一张小表
  `source_refresh_runs`（schema 26）而不是只靠 tasks 结果 JSON：P-04 的任务保留期未定，过期后
  `verified_through` 不能凭空消失。fresh-init 会清掉它——这正确：新库还没验证过，日更 item
  按 §5.1 的 H 闸门先 fail-closed，等第一次 full 后再发布。
- 调度：由日更 Skill 在 `run_market_update` **之前**调 `tail`；每周固定一天调 `full`。两者都不在
  写循环计时内（§6）。刷新必须与 `data_service` 同进程：写 `exchange_source_snapshots` 要数据库租约，
  而 `source_store` CLI 的写库 scope 要求停服（`docs/source-store.md` §4.2）；为每周 46 min 的刷新
  停一次服不可接受。这也是 Q5 推荐 MCP 工具而不是 CLI 的原因。

**R2b 补充（运行语义，2026-11-02）**

- **单飞**：开始新 run 前，在同一个写事务里检查是否已有 `status='running'` 的 run；有则
  拒绝并返回稳定错误码 `refresh_already_running`（`details.run_id` 指向那个 run）。
  `tail` 与 `full` 互斥：约束在 run 记录上，不按 mode 各放一个。理由：两个并发 run 各自
  按 1 req/s 限速，合起来就是 2 req/s，违反 XDM-143；单飞让“单 Client 1 req/s”等于
  “全局 1 req/s”。
- **同步/异步**：`tail` 保持同步（28 个计划请求；探针触发整表是上界例外，最多 549 个）。
  `full` 异步：校验并写好 run 记录后立即返回 `{run_id, status:"running"}`，实际抓取在
  `data_service` 进程内的后台线程执行，写入仍经写协调器。客户端断开不影响后台 run；
  服务停止会中断它（下次启动按下面的回收规则处理）。
- **查询**：同一个工具的 `{"status_of":"<run_id>"}`，返回 run 记录
  （mode/status/scope/起止时间/requests/reused/changed/failed_windows/`verified_through`/
  失败列表），不启动任何 run；未知 id 为 `refresh_run_not_found`。计数与
  `verified_through` 只在 run 结题时一次写入，所以 `running` 回包里的计数恒为 0：它是
  “谁在跑、跑到什么时候”的记录，不是进度条。per-source 行在库里，R3 直接读。
- **panic 当场结题**：`tail` 与后台 `full` 共用执行入口，抓取过程 `catch_unwind`；
  panic 时 run 行立即写 `failed`（失败码 `refresh_panicked`，detail 为 panic 文本，
  超长截断），不推进 `verified_through`，单飞闸门立即释放。只有进程退出才靠下一次启动
  回收——包括 panic 落在写协调器内部、连结题那次写都做不了的情形。
- **回收遗留 running 行（仅进程退出）**：`data_service` 拿到数据库租约启动时，把上一个进程实例留下的
  `running` 行标成 `failed`（失败码 `process_restarted`），**不**推进 `verified_through`。
  归属判断用进程实例 id（`source_refresh_runs.owner_instance`，即本进程的 run id），
  不用已过时间猜：同一进程正在跑的 full 不会被自己的启动逻辑回收。
  回收后单飞闸门自动解开；`verified_through` 只能由完整的成功 run 推进
  （`latest_complete_verified_through` 只读 `succeeded` 且 `complete=1` 的来源行，
  被回收的 run 根本没有来源行）。
- **每来源墙钟**：`source_refresh_run_sources.elapsed_ms` 记该来源从第一个请求到结束的
  墙钟毫秒（向上取整），由 `execute` 按来源写入。G2 的每表门禁读这一列（D-67）：两表同日
  触发合计约 780 s，按 run 总量记账会把正常成本判成违规。
- **取舍**：异步 full 需要一条只能由服务自己恢复的“遗留 running”状态，因此新增
  `owner_instance` 列（026 未部署，直接改 026）；没有为状态查词另开读工具，而是复用同一工具的
  `status_of` 参数，避免多一个工具进 `tools/list` 预算与 Skill 白名单。`tail` 不做异步：它的
  SLO 是 <300s（G2），一次调用能等完，且日更编排需要它的结果作为下一步输入。

## 6. D-63 / SLO 第 2 行：修订（owner 2026-11-01 已裁决）

**已落地文本（[SLO](../SLO.md) 第 2 行、[DECISIONS](../decisions.md) D-66）：**

1. 第 2 行拆成两个门禁，**门槛不放宽**：

     `full` <60 min（1,941 请求 × 1.42 s

2. 来源 item 的**陈旧闸门**替代“获取必须发生在日更里”：`today - verified_through > 14 天` →
   四个 item fail-closed，旧版本可读。
3. **如实写明 G1 仍会红**：本代 G1 ≈ 3,009.6 − 2,400.7 = **609 s**（还不含本地解析），即使把
   获取全部移出也高于 600 s；551.8 s 的实体路径 + 44 s 日历 + 9.8 s 启动 = 605.6 s 已是下限。

   660 s 或把起点挪到第一个实体 item（后者会得到 599.2 s，纯属噪声边缘）。
4. D-63 的“连续 3 次”计数规则不变；本代与 11-02/11-03 两代按 owner 裁决不计入，不追溯。

备选（**未采用**）是把第 2 行定义为“**日更写循环 + 当日 tail**”，full 单独成行；

## 9. 六个扩展场景走查

先读 [design.md](../design.md)「后续数据扩展要求」。本设计与其一致：刷新是**来源适配器 + 一处策略
登记**；新增数据类别仍走独立模型。

| # | 场景 | 刷新层要改什么 | 领域/契约要改什么 | 能否“只改适配层 + 一处登记” |
|---|---|---|---|---|
| 1 | 新增证券类型（ETF/指数/北交所/B 股） | 新增来源的 `source_id` + 策略行（整表/窗口、P/H）；若沿用交易所名单，只是多一个 plan | ETF 身份名单、`price_scale`、`cat11`；北交所的目录 scope/名单/ST 分档；B 股币种/代码规则 | **ETF/北交所/B 股：不能**（结构差异，D-28 另拆）；**指数：能**（已在 M1） |
| 2 | 新增官方来源（如证监会行业分类） | 新 adapter + `source_id` + 策略行；若是文件型来源，走 `archive_import`/`generation_member`，**不进 HTTP 刷新** | 新口径的独立模型 + 映射 + 双 scheme 读面 | **获取能；写面不能**（口径不同需独立模型） |
| 3 | 新增字段/数据集（财务） | 新的 `source_id` + 策略行；复用 tail/full/陈旧闸门 | 独立表 + 迁移 + 读模型 + 导出文件 + `derived_dataset_versions` 登记 | **刷新能；数据集不能**（新类别独立模型） |
| 4 | 新增频率（分钟线） | 若是新的高频来源，需要新的刷新节奏（分钟级），现有 tail/full 模型不适用 | 新 `period`/表 + 秒级时间 + 主键语义 | **不能**：分钟级获取的调度/去重/存储是另一套模型 |
| 5 | 交易规则变更（涨跌停） | 无需改刷新（规则是数据行）；但 ST 区间的陈旧上界会直接影响涨跌停带 | 规则表一行（M2） | **能**（数据变更）；前提是 Q4 的 `known_at` 诚实 |
| 6 | 新增使用方/入口（x 之外的回测/导出） | 新使用方读同一份“最新完整快照集”，不改获取；若要新来源，加策略行 | 新入口适配/格式 writer + 入口预算 + 封闭性测试 | **能**：入口枚举 + 静态表；代价是每个入口的 systemd/探针 |

分离点落位：

| 分离点 | 本设计 |
|---|---|
| 来源适配器 vs 领域 | 策略、复用、探针、full 全在 `exchange_source`/refresh 任务；领域只拿 `SnapshotSet{ids, as_of, verified_through}` |
| 原始证据 / 解析事实 / 派生 | 复用只改“原始证据怎么来”；解析与派生仍只从字节算，字节是唯一真相 |
| 有效时间 vs 知晓时间 | `as_of`（字节首见）/`known_at`（事实首见）/`verified_through`（确认未变）三字段分开，复用不推进前两个 |
| 编排 vs 原子能力 | refresh 是原子任务（tail/full）；`run_market_update` 只做派生；Skill 负责顺序 |
